# Спека: VPN-координатор (v2, схема LOCAL → REMOTE)

Статус: **готова к разработке** (все вопросы решены 2026-10-12, раздел 13).

Требования пронумерованы (`R-...`), критерии приёмки (`AC-...`) — для spec-driven разработки: каждая задача ссылается на номера, каждый AC проверяется тестом или ручным прогоном.

---

## 1. Цели и не-цели

**Цели**

- R-G1. Клиент в стране «отправления» подключается одним AWG-туннелем к LOCAL; трафик в «свою» страну выходит с LOCAL, всё остальное — с REMOTE через межсерверный AWG-туннель.
- R-G2. Доступ к сети есть только у участников заданного Telegram-чата (как сейчас).
- R-G3. Координатор — единственное место, где описана и хранится система: декларативный конфиг серверов + БД с пользователями/ключами. Серверы — «скот»: их состояние целиком выводится из конфига и БД.
- R-G4. **Замена сервера = замена адреса (и пароля) в конфиге.** Дальше координатор сам настраивает чистую Ubuntu 24.04 по SSH и переносит на неё всё состояние. Никаких ручных действий на серверах.
- R-G5. API для клиентского приложения: вход через код из Telegram-бота, выпуск конфигов с уникальным id, проверка актуальности конфига и доступности серверов.
- R-G6. Отказ координатора не ломает работающий VPN: серверы работают автономно, недоступны только выпуск/отзыв конфигов и вход.

**Не-цели v1**

- Клиентское приложение. Потребитель API — форк AmneziaVPN, который сам заменяет конфиг при изменении конфигурации; здесь описан только API-контракт для него.
- Учёт трафика, биллинг, мониторинг использования (как и сейчас).
- Балансировка/автоматический failover между несколькими LOCAL или REMOTE.
- IPv6 внутри туннеля (блокируется, чтобы не было утечек). 
- Доменная маршрутизация (только по IP/CIDR).
- Дополнительный управляющий туннель: координатор ходит на серверы по SSH на outer-адреса напрямую.

## 2. Глоссарий

| Термин | Значение |
|---|---|
| LOCAL | Сервер в стране отправления. Адреса: `client` (сюда подключаются клиенты), `outer` (выход «домашнего» трафика + SSH), `tunnel` (источник туннеля до REMOTE). |
| REMOTE | Сервер в стране назначения. Адреса: `outer` (выход трафика + SSH), `tunnel` (принимает туннель от LOCAL). |
| Площадка (site) | Пара LOCAL + REMOTE, связанная туннелем. В v1 одна, модель данных — список. |
| Узел (node) | Логическая роль `<site>/local` или `<site>/remote`. Имеет **идентичность** (ключи, порты, параметры обфускации), которая хранится в БД координатора и переживает замену физической машины. |
| Хост | Конкретная машина по конкретному адресу. Заменяемая. |
| Конфиг клиента | AWG-конфиг устройства для подключения к LOCAL. Имеет `id` (UUID) и `revision`. |
| Ревизия | Хеш всех полей, из которых рендерится текст конфига клиента. Меняется, если клиенту нужно перезабрать конфиг. |

## 3. Топология

```
                 страна отправления                         страна назначения
 ┌────────┐ AWG  ┌──────────────────────────────┐   AWG    ┌──────────────────────────┐
 │ клиент ├─────►│ LOCAL.client   awgc          │          │            REMOTE        │
 └────────┘      │                              │          │                          │
                 │  geo-ip: «своя» страна? ──да─┼─► LOCAL.outer ─► интернет           │
                 │                 └─нет─► awgt │ LOCAL.tunnel ──► REMOTE.tunnel awgt │
                 └──────────────────────────────┘          │      └─► REMOTE.outer ─► интернет
                                                           └──────────────────────────┘
 координатор ──SSH──► LOCAL.outer, REMOTE.outer       клиентское приложение ──HTTPS──► координатор
```

## 4. Сетевая схема узлов

Все значения ниже (подсети, порты, марки) — дефолты, переопределяются в конфиге.

### 4.1 Общее для обоих узлов

- R-N1. ОС: Ubuntu 24.04. Иначе провижининг падает с понятной ошибкой.
- R-N2. AmneziaWG ставится нативно (модуль ядра через `ppa:amnezia/ppa`, `amneziawg` + DKMS), интерфейсы управляются `awg-quick@<iface>`. Docker на узлах не используется.
- R-N3. Дополнительные адреса (хостер RUVDS) админ прописывает на хосте сам. Провижининг их **не настраивает**, а только проверяет: если какого-то адреса из конфига нет на интерфейсах, узел не применяется, админу уходит алерт с понятной ошибкой. (Решение Q-B7; автодобавление через netplan можно вернуть позже.)
- R-N4. `net.ipv4.ip_forward=1`, `rp_filter=2` (loose, из-за policy routing), IPv6-форвардинг выключен.
- R-N5. Файрвол nftables, политика `drop` на input: разрешены established/related, ICMP, SSH (22) только на `outer`, UDP-порт AWG только на соответствующий адрес (см. ниже). Весь файрвол рендерится координатором целиком в `/etc/nftables.conf`.
- R-N6. Параметры обфускации AWG (`Jc, Jmin, Jmax, S1–S4, H1–H4` и пр.) генерируются координатором один раз для каждого интерфейса и хранятся в идентичности узла.
- R-N7. На узле есть маркер `/etc/vpn-node/node.json`: `{ node, role, appliedHash, appliedAt, coordinatorVersion }`.

### 4.2 LOCAL

| Интерфейс | Адрес | Назначение |
|---|---|---|
| `awgc` | `10.66.0.1/16` (клиентская подсеть) | Сервер для клиентов, `ListenPort = Pc`. nft пропускает UDP `Pc` только на `daddr = LOCAL.client`. |
| `awgt` | `10.255.0.1/30` | Клиент туннеля до REMOTE: `Endpoint = REMOTE.tunnel:Pt`, `AllowedIPs = 0.0.0.0/0`, `Table = off`, `FwMark = 0x51`. |

- R-L1. **Исходящий адрес туннеля.** `ip rule fwmark 0x51 lookup 151`; в таблице 151 `default via <gw> dev <nic> src LOCAL.tunnel`. Так UDP-пакеты `awgt` уходят с `LOCAL.tunnel`.
- R-L2. **Geo-ip.** nft-набор `geo_home` (`ipv4_addr`, `flags interval`) = CIDR страны `local.country` ∪ `routing.alwaysDirect`; набор `force_remote` = `routing.alwaysRemote`. Источник — db-ip Lite (CC BY), координатор скачивает раз в неделю и раскатывает на LOCAL.
- R-L3. **Маркировка.** В prerouting (mangle) для `iifname awgc`: если `daddr ∈ force_remote` → mark `0x52`; иначе если `daddr ∈ geo_home` или RFC1918 → без марки; иначе → mark `0x52`. `ip rule fwmark 0x52 lookup 152`; таблица 152: `default dev awgt`.
- R-L4. **NAT.** `oifname <nic> ip saddr 10.66.0.0/16 snat to LOCAL.outer`; `oifname awgt ip saddr 10.66.0.0/16 snat to 10.255.0.1` (REMOTE не знает о клиентской подсети — меньше связности при замене).
- R-L5. Трафик клиент↔клиент запрещён (`iifname awgc oifname awgc drop`). MSS clamp на forward.
- R-L6. **REMOTE недоступен:** трафик, помеченный на REMOTE, просто не проходит (fail-closed), домашний работает, админу уходит алерт (R-H4). (Решение Q-B5.)
- R-L7. Обновление geo-набора атомарное (`nft -f` с `flush set` + `add element` в одной транзакции). Если новая выгрузка не скачалась или подозрительно мала (< 50% от предыдущей), остаётся старый набор.

### 4.3 REMOTE

| Интерфейс | Адрес | Назначение |
|---|---|---|
| `awgt` | `10.255.0.2/30` | Сервер туннеля, `ListenPort = Pt`. nft пропускает UDP `Pt` только на `daddr = REMOTE.tunnel` и `saddr = LOCAL.tunnel`. |

- R-R1. NAT: `oifname <nic> ip saddr 10.255.0.0/30 snat to REMOTE.outer`.
- R-R2. Исходящие пакеты туннеля REMOTE отправляет с адреса, на который пришёл пакет (поведение WireGuard), отдельная маршрутизация не нужна.
- R-R3. **DNS для клиентов:** в конфиге клиента `DNS = 1.1.1.1, 8.8.8.8`. По geo-ip это зарубежные адреса, поэтому запросы идут через REMOTE и не подменяются на стороне страны отправления; своих резолверов на узлах нет.

### 4.4 MTU

- R-M1. `awgt` MTU = 1380, клиентский конфиг MTU = 1280 (с запасом под двойную инкапсуляцию и паддинг S3/S4). Значения в конфиге; проверяются AC-N4.

## 5. Декларативный конфиг координатора

Один YAML-файл (по умолчанию `/etc/vpn-coordinator/config.yaml`, права 600, не в git). Пароли могут быть указаны прямо или ссылкой на переменную окружения (`${VAR}`).

```yaml
telegram:
  botToken: ${TELEGRAM_BOT_TOKEN}
  chatId: -1001234567890          # членство в этом чате = доступ
  admins: [123456789]              # tg id: технические алерты и админ-команды
  announceOutages: true            # падение/восстановление сети дублировать в чат chatId

api:
  listen: 127.0.0.1:8080            # за reverse proxy с TLS
  publicUrl: https://vpn.example.com

clients:
  subnet: 10.66.0.0/16
  mtu: 1280

routing:
  geoSource: dbip-lite              # раз в неделю
  alwaysDirect: []                  # CIDR, всегда через LOCAL.outer
  alwaysRemote: []                  # CIDR, всегда через REMOTE

sites:
  - name: main
    local:
      country: RU
      ssh: { user: root, password: ${MAIN_LOCAL_PASSWORD}, port: 22 }
      addresses:                    # можно с префиксом: 203.0.113.10/24
        client: 203.0.113.10
        outer:  203.0.113.11        # SSH идёт сюда
        tunnel: 203.0.113.12
    remote:
      country: NL                   # необязательно: страна выхода, имя сервера в приложении
      ssh: { user: root, password: ${MAIN_REMOTE_PASSWORD} }
      addresses:
        outer:  198.51.100.20       # SSH идёт сюда
        tunnel: 198.51.100.21
```

- R-C1. Конфиг валидируется схемой при старте и при каждом перечитывании; невалидный конфиг не применяется, админу уходит алерт, продолжает действовать последний валидный.
- R-C2. Изменения конфига применяются автоматически (файл перечитывается на каждом цикле реконсиляции и по изменению файла), `/apply` — применить немедленно.
- R-C3. Пользователь `ssh.user` — `root` или пользователь с sudo (тогда `sudo -S` с тем же паролем).
- R-C4. Чего в конфиге нет и не должно быть: ключей, портов, параметров обфускации, внутренних адресов. Это идентичность узла, она в БД (раздел 6) и генерируется автоматически.

## 6. Состояние координатора (SQLite)

| Таблица | Поля (основные) |
|---|---|
| `users` | `tg_id` PK, `username`, `status` (`active`/`suspended`), `membership_checked_at`, `created_at` |
| `login_codes` | `code_hash`, `tg_id`, `expires_at`, `used_at` |
| `device_tokens` | `token_hash` PK, `tg_id`, `label`, `created_at`, `last_seen_at`, `revoked_at` |
| `client_configs` | `id` (UUID) PK, `tg_id`, `name`, `address`, `private_key`, `public_key`, `preshared_key`, `state` (`active`/`suspended`/`revoked`), `created_at`, `revoked_at`; уникальность `(tg_id, name)` среди не-`revoked` |
| `nodes` | `name` PK (`main/local`), `role`, `identity` (JSON: приватные ключи интерфейсов, порты, параметры обфускации, внутренние адреса), `created_at` |
| `hosts` | `node`, `address`, `host_key` (TOFU), `applied_hash`, `last_ok_at`, `last_error`, `health` |
| `geo_sets` | `country`, `cidrs`, `source`, `fetched_at` |

- R-S1. Пользователь идентифицируется по Telegram id, а не по username (сейчас — username, это ломается при его смене). Username хранится только для отображения.
- R-S2. Ключи клиента генерирует координатор (нужно для выдачи `.conf` через бота и для перевыпуска). Адрес — первый свободный в подсети среди не-`revoked` конфигов.
- R-S3. **Идентичность узла создаётся один раз** при первом появлении площадки в конфиге и не меняется при замене хоста. Поэтому после замены LOCAL у клиента меняется только `Endpoint`, ключ сервера и обфускация остаются прежними.
- R-S4. Токены устройств и коды входа хранятся только хешами.
- R-S5. Бэкап: раз в сутки (и по `/backup`) архив из БД (`sqlite3 .backup`), `config.yaml` и SSH-ключа координатора → шифрование `age` публичным ключом из `/etc/vpn-coordinator/backup.pub` → файл админу в Telegram. Приватный ключ только у админа. Без SSH-ключа в бэкапе восстановиться нельзя: вход по паролю на узлах отключён.

## 7. Провижининг и реконсиляция

### 7.1 Цикл реконсиляции

- R-P1. Раз в 5 минут, по изменению БД (добавлен/отозван конфиг) и по `/apply` координатор для каждого узла:
  1. Рендерит **желаемое состояние** — набор файлов (awg-конфиги, nftables, sysctl, systemd-юниты, geo-набор) и считает `desiredHash`. Рендер — чистая функция `(config, db) → files`, покрыта юнит-тестами.
  2. Подключается по SSH к `outer`. Ключ координатора, если есть, иначе пароль.
  3. Читает `/etc/vpn-node/node.json`. Нет файла или другой `node` → **bootstrap** (7.2). `appliedHash ≠ desiredHash` → **apply** (7.3). Равно → только health-check (8).
- R-P2. Узлы обрабатываются параллельно, но операции над одним узлом сериализованы (мьютекс на узел).
- R-P3. Ошибки не роняют процесс: пишутся в `hosts.last_error`, повтор на следующем цикле с экспоненциальной паузой (до 30 мин), админу — алерт при первой ошибке и при восстановлении.

### 7.2 Bootstrap чистой Ubuntu 24.04

Идемпотентный скрипт, загружаемый по SSH; любой шаг можно перезапустить.

1. Проверка ОС и архитектуры.
2. Установка публичного SSH-ключа координатора в `authorized_keys`; после проверки входа по ключу — `PasswordAuthentication no`.
3. `apt update && apt full-upgrade`, установка `nftables`, `amneziawg` (PPA), `linux-headers-$(uname -r)`, `unattended-upgrades` (с автоперезагрузкой ночью).
4. Если обновилось ядро или DKMS-модуль не собран → перезагрузка, ожидание до 5 минут, продолжение.
5. Дальше — как apply (7.3).

### 7.3 Apply

1. Файлы желаемого состояния заливаются одним tar-архивом через stdin SSH во временный каталог.
2. `apply.sh` на узле раскладывает их, применяет: `sysctl --system`, `nft -f`, `systemctl enable --now awg-quick@…`, для изменений только в пирах `awgc` — `awg syncconf awgc <(awg-quick strip awgc)` без разрыва соединений (как в текущем коде).
3. Самопроверка на узле (интерфейсы подняты, правила на месте) и запись `node.json` с новым `appliedHash`.
- R-P4. Изменение только списка клиентов на LOCAL применяется за < 10 секунд и не рвёт соединения других клиентов.
- R-P5. На узле нет ничего, что нужно настраивать руками или что зависит от координатора в рантайме: после перезагрузки узел поднимается сам из своих файлов.

### 7.4 SSH host keys

- R-P6. TOFU: ключ хоста запоминается при первом подключении к адресу. Новый адрес → новый TOFU без вопросов (это и есть замена сервера). Тот же адрес, другой ключ → координатор не подключается, алерт админу; админ подтверждает командой `/trust <node>` (например, после переустановки ОС на той же машине).

### 7.5 Сценарии замены (главный сценарий эксплуатации)

| Что случилось | Действие админа | Что делает координатор | Что видит клиент |
|---|---|---|---|
| Умер REMOTE | Новый адрес/пароль REMOTE в конфиге | bootstrap нового REMOTE с той же идентичностью; apply на LOCAL (новый `Endpoint` туннеля, новый `saddr` в nft) | ничего, после восстановления зарубежный трафик снова идёт |
| Умер LOCAL | Новые адреса/пароль LOCAL | bootstrap нового LOCAL с той же идентичностью и всеми пирами; apply на REMOTE (новый разрешённый `saddr`) | статус конфига → `outdated`; приложение само перезабирает конфиг (меняется только `Endpoint`); владельцам `.conf` из бота бот присылает новый |
| Заблокировали один IP (хост жив) | Новый адрес в соответствующем поле | apply (nft, endpoint); новый IP админ сам прописывает на хосте | только при смене `LOCAL.client` — как выше |

## 8. Health-check

- R-H1. На каждом цикле (и отдельно раз в минуту — облегчённо) координатор по SSH читает `awg show all dump` и собирает: LOCAL доступен, `awgc` поднят, `awgt` — последний handshake < 3 минут; REMOTE доступен, `awgt` поднят.
- R-H2. Состояние площадки: `ok` / `degraded` (LOCAL жив, туннель до REMOTE нет — работает только домашний трафик) / `down` (LOCAL недоступен).
- R-H3. Если координатор не может достучаться до узла по SSH, но handshake на другом узле свежий — считать узел живым (`unknown-mgmt`), не алертить как падение VPN (координатор мог потерять связность сам).
- R-H4. Смены состояния → алерт админам в личку (с дебаунсом: 2 подряд неудачных проверки). Падение и восстановление сети (`degraded`/`down`/`ok`) при `announceOutages: true` дополнительно короткой фразой публикуется в чат пользователей; технические ошибки (провижининг, host key, конфиг) — только админам.

## 9. API для клиентов (форк AmneziaVPN)

HTTPS, JSON, префикс `/v1`. Авторизация — `Authorization: Bearer <device-token>`. Ошибки: `{ "error": { "code": "...", "message": "..." } }` с соответствующим HTTP-статусом.

### 9.1 Токен устройства

Поток: пользователь пишет боту `/login` → бот проверяет членство и отвечает кодом из 6 символов (без похожих букв), код живёт 5 минут и одноразовый → пользователь вводит код в приложении → приложение получает **токен устройства** и хранит его у себя.

| Метод | Запрос | Ответ |
|---|---|---|
| `POST /v1/auth/login` | `{ code, deviceLabel? }` | `200 { token, user: { tgId, username } }`; `400 invalid_code` |
| `POST /v1/auth/logout` | — | `204` (токен этого устройства отозван) |

- R-A1. Перебор кодов: не больше 5 попыток в минуту с IP; конкретный код сгорает после 5 неудачных попыток.
- R-A2. Токен привязан к пользователю, бессрочный. Отзывается: `/logout` из приложения; вместе со всеми токенами пользователя, когда пользователь отозван (вышел из чата, `/revoke_user`).
- R-A3. Любой запрос с токеном пользователя, который сейчас не участник чата (по кэшу, не старше часа), → `403 not_member`; при возвращении в чат токены не восстанавливаются, нужен новый `/login`.
- R-A4. В боте `/devices` показывает токены пользователя (метка, последний визит) с возможностью отозвать любой.

### 9.2 Конфиги

| Метод | Запрос | Ответ |
|---|---|---|
| `GET /v1/me` | — | `{ user, configs: [ConfigSummary] }` |
| `POST /v1/configs` | `{ name }` (`[a-z0-9-]{1,32}`) | `201 Config`; `409 name_taken` |
| `GET /v1/configs/{id}` | — | `Config` (текущий рендер) |
| `GET /v1/configs/{id}/status?revision=…` | — | `ConfigStatus` |
| `DELETE /v1/configs/{id}` | — | `204` |

Все эндпоинты требуют токен; пользователь видит и меняет только свои конфиги (чужой id → `404`).

```jsonc
// Config
{ "id": "uuid", "name": "phone", "revision": "a1b2c3d4", "createdAt": "…",
  "awg": "[Interface]\n…",            // полный текст .conf
  "vpnKey": "vpn://…",                 // тот же конфиг в формате ключа AmneziaVPN (description = serverName)
  "endpoint": "203.0.113.10:51820",
  "serverName": "🇳🇱 Нидерланды" }     // имя сервера в приложении: флаг + страна remote.country (без неё — имя площадки); входит в revision

// ConfigStatus
{ "state": "ok" | "outdated" | "suspended" | "revoked",
  "revision": "a1b2c3d4",             // актуальная
  "network": "ok" | "degraded" | "down",
  "checkedAt": "…" }
```

- R-A5. `outdated` = переданная `revision` ≠ текущей.
- R-A6. `network` берётся из последнего health-check (раздел 8), а не проверяется синхронно.
- R-A7. Лимита на число конфигов у пользователя нет.

### 9.3 Автообновление в приложении

- R-A8. Приложение хранит токен устройства и для каждого своего конфига `id` + `revision`. При запуске, при ошибке подключения и раз в N минут оно вызывает `status`; на `outdated` забирает `GET /v1/configs/{id}` и подменяет конфиг без участия пользователя; на `suspended`/`revoked` и `403 not_member` показывает причину.
- R-A9. Конфиги, выданные ботом (`/add`), тоже принадлежат пользователю: после входа в приложение они видны в `GET /v1/me` и обновляются так же. Без входа `.conf` из бота работает как обычный статический конфиг.
- R-A10. Изменения API только обратно совместимые (`/v1`), потому что старые версии форка останутся у пользователей.

## 10. Telegram-бот

Пользовательские команды (только в личке, только участникам чата, как сейчас):

- `/start`, `/info` — список устройств и команд.
- `/add <name>` — выпуск конфига; QR + `.conf`, автоудаление через 5 минут (как сейчас). Тот же код выпуска, что в API.
- `/remove <name>` — отзыв.
- `/login` — код для входа в приложение (9.1).
- `/devices` — устройства, где выполнен вход, с возможностью отозвать.

Админские команды (только `telegram.admins`): `/status` (здоровье площадок и узлов, последние ошибки, версии приложений у пользователей), `/apply` (реконсиляция сейчас), `/apply upgrade` (то же + `apt upgrade` на узлах), `/trust <node>`, `/rotate tunnel|clients`, `/revoke_user <@username|id>`, `/backup`.

- R-B1. Почасовая проверка членства всех известных пользователей (как сейчас, с ретраями). Вышел из чата → его конфиги `suspended` (пиры убираются с LOCAL), сессии отзываются. Вернулся → при следующем обращении к боту конфиги снова `active` (токены устройств — нет, нужен новый `/login`).
- R-B2. Если бот — админ чата, дополнительно обрабатываются апдейты `chat_member` для мгновенного отзыва; почасовая проверка остаётся как страховка.

## 11. Технологии и развёртывание координатора

- Node.js 22 + TypeScript (как сейчас), один процесс: бот + HTTP API (fastify) + реконсилер + cron. SQLite (`better-sqlite3`), SSH — `ssh2`, валидация конфига — `zod`.
- Развёртывание — pm2 как сейчас (или systemd), TLS — Caddy перед API. Координатор живёт на текущем сервере, API на поддомене с TLS (решение Q-C1/Q-C2).
- Скрипты провижининга (bash) лежат в репозитории, рендерятся шаблонами, покрыты юнит-тестами рендера.
- Тестовый стенд: две ВМ Ubuntu 24.04 (multipass/LXD VM) с дополнительными адресами — для AC раздела 12.

## 11a. Эксплуатация и версии протокола

- R-O1. В поставку входит инструкция по эксплуатации ([runbook.md](runbook.md)); любое изменение команд, путей и сценариев обновляет её в том же PR.
- R-O2. Скрипты `npm run check-config` (валидация `config.yaml` без запуска) и `npm run restore -- <backup.tar>` (раскладка БД, конфига и SSH-ключа из расшифрованного бэкапа).
- R-O3. **Профили протокола.** Генерация параметров обфускации и рендер AWG-конфигов идут через «профиль протокола» (`awg2`, `awg3` = AmneziaWG 3.1 — по умолчанию с 2026-10-13 …): модуль, который знает набор параметров версии и умеет их сгенерировать. В конфиге `tunnel.protocol` и `clients.protocol` (по умолчанию — текущая версия). Смена профиля = генерация новых параметров для соответствующих интерфейсов, сохранение в идентичность узла, apply.
- R-O4. `/rotate tunnel|clients` — перегенерировать параметры обфускации в текущем профиле (на случай, если текущие начали детектировать).
- R-O5. Смена параметров клиентского интерфейса меняет ревизию всех конфигов; владельцам конфигов, выданных ботом и ни разу не обновлённых через приложение, бот сам присылает новый конфиг. То же при смене `LOCAL.client`.
- R-O6. Приложение передаёт свою версию (`X-App-Version`) в каждом запросе; координатор хранит последнюю версию на токен устройства и показывает распределение в `/status` — чтобы понимать, можно ли переключать клиентский протокол.

## 12. Критерии приёмки

Сеть
- AC-N1. С клиента: `curl ifconfig.me` → `REMOTE.outer`; запрос к сервису с IP «своей» страны (например, `yandex.ru/internet`) показывает `LOCAL.outer`.
- AC-N2. CIDR из `alwaysDirect`/`alwaysRemote` маршрутизируются вопреки geo-ip.
- AC-N3. При остановленном REMOTE домашний трафик работает, зарубежный — нет; утечек через `LOCAL.outer` нет (`tcpdump`).
- AC-N4. Загрузка сайта и `ping -M do -s 1252` с клиента проходят без фрагментации.
- AC-N5. DNS-запросы клиента к `1.1.1.1`/`8.8.8.8` выходят с REMOTE.outer; IPv6 с клиента недоступен и не течёт.
- AC-N6. Порт AWG LOCAL не отвечает на `outer`/`tunnel`, SSH не отвечает на `client`/`tunnel`.

Эксплуатация
- AC-P1. Чистая Ubuntu 24.04 + адрес/пароль в конфиге → через ≤ 15 минут узел полностью рабочий без ручных действий.
- AC-P2. Замена REMOTE в конфиге → клиенты ничего не перенастраивают, зарубежный трафик восстанавливается.
- AC-P3. Замена LOCAL → статус конфигов `outdated`, после перезабора конфига всё работает; ключи клиента и сервера те же, отличается только `Endpoint`.
- AC-P4. Перезагрузка любого узла → он поднимается сам, координатор не нужен.
- AC-P5. Повторный apply без изменений ничего не меняет на узле (идемпотентность), повторный bootstrap на уже настроенном узле безопасен.
- AC-P6. Остановленный координатор не влияет на работающий VPN.

Доступ и API
- AC-A1. Не-участник чата не получает ни кода, ни конфига; выход из чата → в течение часа пиры убраны, токены недействительны, статус `suspended`.
- AC-A2. Код входа одноразовый и истекает через 5 минут; выход из чата отзывает все токены устройств пользователя.
- AC-A3. Добавление/удаление конфига применяется на LOCAL ≤ 10 секунд, остальные клиенты не переподключаются.

### Решено (2026-10-12)

- Q-A1. Клиент — форк AmneziaVPN, автоматически обновляет конфиги через API (9.3).
- Q-A2. Вход в v1: токен устройства через код из бота; токены отзываются вместе с пользователем (9.1).
- Q-A3. Лимита устройств нет.
- Q-A4. Вышел из чата — конфиги приостанавливаются, при возвращении включаются снова.
- Q-A5. В `Endpoint` конфига — IP; при замене LOCAL приложение само перезабирает конфиг.
- Q-B1. В v1 одна площадка, модель данных — список.
- Q-B2. Geo-ip — db-ip Lite, раз в неделю.
- Q-B3. Ручные CIDR-списки «всегда напрямую» / «всегда через REMOTE»; доменов в v1 нет.
- Q-B4. DNS клиентов — публичные резолверы `1.1.1.1, 8.8.8.8`, идут через REMOTE; unbound не ставим.
- Q-B5. REMOTE недоступен — fail-closed + алерт.
- Q-B6. Только IPv4, IPv6 в туннеле блокируется.
- Q-B8. AmneziaWG на узлах нативно (модуль ядра из PPA), без Docker.
- Q-B7. Хостер RUVDS, доп. адреса прописывает админ, провижининг только проверяет.
- Q-C1/C2. Координатор на текущем сервере, API на поддомене с TLS.
- Q-C3. После первой настройки — ключ координатора, вход по паролю отключается.
- Q-C4. Алерты — админу в личку; падение/восстановление сети — ещё и в чат пользователей.
- Q-C5. Бэкап БД раз в сутки, зашифрованный, файлом админу в Telegram.
- Q-C6. Изменения конфига применяются автоматически + `/apply`.
- Q-D1/D2. Всем перевыпускаются конфиги, импорта и параллельной работы нет; переход координирует админ вручную.
