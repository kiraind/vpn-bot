# Инструкция по эксплуатации VPN (схема LOCAL → REMOTE)

Описывает целевую систему из [coordinator-spec.md](coordinator-spec.md). Команды и имена файлов — те, что зафиксированы в спеке; инструкция входит в поставку и обновляется вместе с кодом (R-O1 в спеке).

Обозначения: **[бот]** — команда админа в личке боту; **[коорд]** — команда на сервере координатора по SSH; **[хостер]** — действие в панели хостера.

---

## 0. Что где лежит

| Что | Где | Зачем |
|---|---|---|
| Конфиг серверов | `/etc/vpn-coordinator/config.yaml` (600) | адреса, пароли первого входа, чат, админы |
| БД | `/var/lib/vpn-coordinator/state.db` | пользователи, конфиги, ключи и параметры серверов |
| SSH-ключ координатора | `/var/lib/vpn-coordinator/ssh/id_ed25519` | единственный способ попасть на LOCAL/REMOTE после первой настройки |
| Код | `/opt/vpn-coordinator` (git) | процесс `vpn-coordinator` под pm2 |
| Секреты для конфига | `/opt/vpn-coordinator/.env` (600, необязательно) | значения для `${VAR}` в `config.yaml` (токен бота, пароли); читается только при старте процесса |
| Публичный ключ бэкапов | `/etc/vpn-coordinator/backup.pub` | шифрование ежедневного бэкапа |
| **Приватный ключ бэкапов** | **только у админа, офлайн** (менеджер паролей) | без него бэкап бесполезен |

Ежедневный бэкап (файл `vpn-backup-YYYY-MM-DD.tar.age` в личке от бота) содержит БД, `config.yaml` и SSH-ключ координатора — этого достаточно, чтобы поднять всё с нуля.

## 1. Первый деплой

### 1.1 Подготовка (один раз)

1. **[хостер]** DNS: A-запись поддомена API (например `vpn.example.com`) → IP сервера координатора.
2. На своём компьютере поставить [age](https://github.com/FiloSottile/age) (`brew install age` на macOS, `apt install age` на Ubuntu; `age-keygen` входит в пакет) и сгенерировать ключ бэкапов: `age-keygen -o vpn-backup.key`. Файл `vpn-backup.key` убрать в менеджер паролей, строку `public key: age1...` сохранить — она понадобится на шаге 1.2.5.
3. **[хостер]** RUVDS: сервер LOCAL на Ubuntu 24.04 с **тремя** IPv4 (client, outer, tunnel). Дополнительные адреса прописать на сервере так, как предлагает RUVDS (координатор их только проверяет). Записать root-пароль.
4. **[хостер]** Сервер REMOTE на Ubuntu 24.04 с **двумя** IPv4 (outer, tunnel), адреса так же прописаны. Записать root-пароль.
5. Бот должен быть **админом** чата пользователей (для мгновенной реакции на выход из чата и для объявлений о сбоях).

### 1.2 Установка координатора (отдельный сервер Ubuntu 24.04, один IPv4, открыты 80/443)

1. **[коорд]** Системные пакеты: Node.js 22, git, `caddy`, `age`, `sqlite3`; `npm i -g pm2`.
2. **[коорд]** Код: `git clone https://github.com/kiraind/vpn-bot /opt/vpn-coordinator && cd /opt/vpn-coordinator && npm ci && npm run build`.
3. **[коорд]** Caddy (`/etc/caddy/Caddyfile`):
   ```
   vpn.example.com {
     reverse_proxy 127.0.0.1:8080
   }
   ```
   `systemctl reload caddy` — сертификат выпустится сам.
4. **[коорд]** Конфиг: `mkdir -p /etc/vpn-coordinator && cp examples/config.example.yaml /etc/vpn-coordinator/config.yaml && chmod 600 …`, заполнить: токен бота, `chatId` (у групп он отрицательный, `-100…`; без минуса конфиг не пройдёт проверку), свой tg id в `admins`, `publicUrl`, площадку `main` с адресами и паролями LOCAL/REMOTE.
   - Значения вида `${VAR}` подставляются из окружения; их удобно держать в `/opt/vpn-coordinator/.env` (`chmod 600`), например `TELEGRAM_BOT_TOKEN=…`, `MAIN_LOCAL_PASSWORD=…`.
   - Если хостер даёт не root, а пользователя с sudo — указать его в `ssh.user` и **оставить пароль в конфиге**: после установки ключа вход идёт по ключу, но пароль по-прежнему нужен для `sudo`.
5. **[коорд]** `echo 'age1...' > /etc/vpn-coordinator/backup.pub`.
6. **[коорд]** Старый бот остановить: `pm2 delete vpn-bot`.
7. **[коорд]** Запуск: `npm run pm2:start && npm run pm2:save` (один раз ещё `npm run pm2:startup` для автозапуска).
8. **[коорд]** Проверка конфига: `npm run check-config` — выводит ошибки схемы, если есть.

### 1.3 Первая настройка серверов

Ничего делать не нужно: на первом цикле координатор сам заходит на LOCAL и REMOTE по паролю, ставит свой ключ, отключает пароль и настраивает всё. Следить:

1. **[бот]** `/status` раз в пару минут. Ожидаемый путь узла: `bootstrapping` → (возможна перезагрузка) → `applying` → `ok`. Обычно ≤ 15 минут.
2. Когда площадка `ok`: **[бот]** `/add test`, импортировать конфиг в приложение, проверить:
   - `ifconfig.me` показывает REMOTE.outer;
   - `2ip.ru` (или любой сервис в «своей» стране) показывает LOCAL.outer.
3. **[бот]** `/remove test`.
4. Объявить пользователям переход (рассылку делаешь сам): им нужно поставить форк приложения, войти через `/login` и выпустить конфиг.
5. **[коорд]** Когда старые конфиги больше не нужны: `docker rm -f amnezia-awg2` (и прочие контейнеры старой схемы).

## 2. Повседневная эксплуатация

Почти ничего. Что приходит само:

- ежедневно — файл бэкапа в личку (проверь раз в месяц, что приходит);
- алерты в личку при ошибках провижининга, недоступности узлов, смене host key;
- алерт, если не удалось обновить geo-ip (db-ip): работает прежний набор, повтор раз в сутки, ничего делать не нужно, пока это не длится неделями;
- в чат пользователей — короткие сообщения «сеть частично/полностью недоступна» и «сеть восстановлена».

Раз в месяц:
1. **[коорд]** `apt update && apt upgrade` на сервере координатора (LOCAL/REMOTE обновляются сами, кроме ядра — см. ниже).
2. **[бот]** `/status` — нет ли узлов с хронической ошибкой.

### 2.1 Обновление координатора

1. **[коорд]** `cd /opt/vpn-coordinator && git pull && npm ci && npm run build`.
2. **[коорд]** `npm run pm2:reload`.

   Шаги 1–2 одной командой: `npm run update`.
3. Если новая версия меняет то, что раскатывается на серверы (шаблоны, скрипты), координатор сам сделает apply на следующем цикле; ускорить — **[бот]** `/apply`. Соединения клиентов при этом не рвутся, если не менялись параметры интерфейсов.

### 2.2 Изменить маршрутизацию

Отредактировать `routing.alwaysDirect` / `routing.alwaysRemote` в `config.yaml` → применится само за ≤ 5 минут (или **[бот]** `/apply`).

### 2.3 Ядро на LOCAL/REMOTE

Bootstrap замораживает ядро, с которым сервер пришёл от хостера (`apt-mark hold` на метапакеты ядра): ни bootstrap, ни ночные автообновления не переводят узел на новую серию ядра. Причина: модуль `amneziawg` собирается через DKMS и отстаёт от новых ядер. На первом деплое RUVDS-образ с `linux-azure` при `full-upgrade` уехал с 6.8 на 7.0, модуль не собрался, а один сервер не вернулся из перезагрузки. Остальные пакеты обновляются как обычно.

Новое ядро = новый сервер: переустановить ОС у хостера и **[бот]** `/trust <узел>` (3.4). Проверить, что держится: на узле `apt-mark showhold`.

## 3. Аварии

Общее правило: **сервер не чинить, а заменять**. Всё состояние в координаторе.

### 3.1 REMOTE перестал работать

Симптом: алерт «площадка main: degraded», в чате — «зарубежные сайты недоступны». Домашний трафик работает.

1. Подождать 10–15 минут, если похоже на краткий сбой у хостера (алерт «восстановлена» придёт сам).
2. Если не восстановился: **[хостер]** новый сервер Ubuntu 24.04 с двумя IPv4, адреса прописать.
3. В `config.yaml` заменить у `sites[main].remote` адреса `outer`, `tunnel` и пароль (если пароль лежит в `.env` — поменять его там).
4. **[бот]** `/apply`, следить за `/status` до `ok`. Если менялся `.env` — вместо `/apply` **[коорд]** `npm run pm2:restart`: `.env` читается только при старте, `config.yaml` — на лету.
5. Клиентам ничего делать не нужно. Старый сервер удалить у хостера.

### 3.2 LOCAL перестал работать

Симптом: алерт «площадка main: down», VPN не работает ни у кого.

1. **[хостер]** RUVDS: новый сервер Ubuntu 24.04 с тремя IPv4, адреса прописать.
2. В `config.yaml` заменить у `sites[main].local` адреса `client`, `outer`, `tunnel` и пароль (если пароль лежит в `.env` — поменять его там).
3. **[бот]** `/apply`, следить за `/status` до `ok`. Если менялся `.env` — вместо `/apply` **[коорд]** `npm run pm2:restart`.
4. Приложения пользователей сами заберут конфиги с новым адресом (при запуске или при ошибке подключения). Владельцы `.conf`, выданных ботом, получат от бота новый конфиг в личку.
5. Старый сервер удалить у хостера.

### 3.3 Заблокирован один адрес, сервер жив

1. **[хостер]** заказать новый IP на тот же сервер, прописать его на сервере.
2. В `config.yaml` заменить только этот адрес → **[бот]** `/apply`.
3. Если менялся `LOCAL.client` — клиенты обновятся сами, как в 3.2. Если `outer`/`tunnel` — клиенты ничего не заметят.
4. **[хостер]** старый IP отключить после `ok`.

### 3.4 Сервер переустановлен на том же адресе

Симптом: алерт «host key изменился для main/local» — координатор не подключается, пока ты не подтвердишь (защита от подмены сервера).

1. Убедиться, что переустановка — твоя (или хостера по твоему запросу).
2. Обновить пароль в `config.yaml` (или в `.env` — тогда **[коорд]** `npm run pm2:restart`), если он сменился.
3. **[бот]** `/trust main/local` → координатор настроит сервер заново.

Если ты ничего не переустанавливал — **не подтверждать**, разбираться с хостером.

### 3.5 Ошибка провижининга

Симптом: алерт «main/remote: ошибка apply/bootstrap» с текстом ошибки. Координатор сам повторяет с растущей паузой.

| Текст ошибки | Что делать |
|---|---|
| `address X not present on host` | Прописать недостающий IP на сервере (см. RUVDS) — или исправить опечатку в `config.yaml`. |
| `ssh auth failed` | На новом сервере — неверный пароль в конфиге. На уже настроенном — кто-то удалил ключ координатора: переустановить сервер (3.4) или временно вернуть пароль. |
| `unsupported os` | Переустановить сервер на Ubuntu 24.04. |
| `amneziawg module build failed` | Модуль не собирается под ядро сервера; следующие строки алерта — первые ошибки компилятора. Ядро на узлах заморожено (см. 2.3), поэтому так бывает только на свежем сервере, если образ хостера уже пришёл с ядром, которое модуль не поддерживает. Переустановить сервер на другой образ Ubuntu 24.04 (у RUVDS — без «azure»-ядра, если есть выбор) и **[бот]** `/trust <узел>`; либо дождаться новой версии `amneziawg-dkms` и **[бот]** `/apply`. |
| `ssh timeout` | Сервер или его `outer` недоступен — смотреть панель хостера; если умер — 3.1/3.2. |
| `площадка …: не удалось построить конфигурацию узлов` | Обычно сменили `clients.subnet`, а старые конфиги в неё не попадают: вернуть прежнюю подсеть. Узлы до исправления работают на старой конфигурации. |

### 3.6 Сервер координатора умер

VPN продолжает работать; не работают вход, выпуск и обновление конфигов, бот молчит.

1. **[хостер]** любой сервер Ubuntu 24.04 (можно другой хостер).
2. Выполнить 1.2, шаги 1–3 (без конфига).
3. Взять последний бэкап из лички, расшифровать на своём компьютере: `age -d -i vpn-backup.key vpn-backup-….tar.age > backup.tar`, скопировать на новый сервер, **[коорд]** `npm run restore -- backup.tar` (раскладывает БД, `config.yaml`, SSH-ключ на места; если там уже есть файлы — отказывается, перезаписать: остановить координатор `npm run pm2:stop`, затем `npm run restore -- backup.tar --force`; на работающем процессе БД испортится). `.env` в бэкап не входит — если секреты лежали там, восстановить его из менеджера паролей. После восстановления удалить расшифрованный архив: `shred -u backup.tar` (в нём все ключи).
4. Положить `backup.pub` (1.2.5), запустить (1.2.7).
5. **[хостер]** DNS-запись API → новый IP. Приложения переподключатся сами по домену.
6. **[бот]** `/status` — узлы должны быть `ok` без переустановки (ключ тот же).

Если бэкап потерян: все серверы нужно переустановить (ключа доступа больше нет), все пользователи перевыпускают конфиги.

### 3.7 Нужно срочно отключить пользователя

**[бот]** `/revoke_user @username` — конфиги и токены отзываются сразу, и отзыв постоянный: даже если человек остался в чате, бот и приложение его больше не пускают. Вернуть доступ — `/unrevoke_user @username` (старые конфиги не возвращаются, он выпускает новые). Обычно не нужно: выход из чата приостанавливает доступ автоматически.

## 4. Новая версия протокола AmneziaWG

Протокол меняется в трёх местах: пакеты `amneziawg` на серверах, параметры обфускации в конфигах (`Jc`, `S1–S4`, `H1–H4`, …) и клиентское приложение. Туннель LOCAL↔REMOTE целиком наш, его можно переключать сразу; клиентские устройства — только после обновления приложения.

### 4.1 Нужно сменить только параметры обфускации

Случай: протокол тот же, но текущие параметры начали детектировать/резать.

1. **[бот]** `/rotate tunnel` — новые параметры для LOCAL↔REMOTE; применяется на обоих серверах сразу, клиенты не замечают (короткий разрыв зарубежного трафика).
2. **[бот]** `/rotate clients` — новые параметры для клиентского интерфейса LOCAL. Ревизия всех конфигов меняется, приложения забирают новые сами; владельцам `.conf` из бота бот рассылает новые конфиги. Пока устройство не обновилось, оно не подключится.

Сейчас по умолчанию `awg3` (AmneziaWG 3.1: `HeaderProtectionKey`, `RandomTrailers`, `DisableCookies` и др.) и для туннеля, и для клиентов; пакеты из PPA Amnezia (`amneziawg-dkms`, `amneziawg-tools`) поддерживают 3.1 с августа 2026. `awg2` оставлен как запасной профиль: `tunnel.protocol: awg2` / `clients.protocol: awg2` в `config.yaml`. Переключение в любую сторону — по шагам 4–6 ниже.

### 4.2 Вышла новая версия протокола (например AWG 3.1 → 4)

1. **Проверить совместимость.** Прочитать changelog `amneziawg` / AmneziaVPN: совместима ли новая версия серверного пакета со старыми клиентами. Если совместима — достаточно шага 2, протокол переключать не нужно.
2. **Серверные пакеты.** LOCAL/REMOTE обновляют пакеты сами (unattended-upgrades); принудительно — **[бот]** `/apply upgrade` (apt upgrade + перезапуск интерфейсов, короткий разрыв).
3. **Координатор.** Выпустить версию координатора, которая умеет генерировать параметры нового протокола (новый профиль в `src/protocol/`) — задача разработки. Обновить координатор (2.1).
4. **Туннель.** В `config.yaml` → `tunnel.protocol: <новый профиль>` → **[бот]** `/apply`. Проверить `/status`: `awgt` handshake свежий. Откат — вернуть старое значение.
5. **Приложение.** Выпустить версию форка с поддержкой нового протокола, дождаться, пока обновится большинство. Сколько устройств уже на новой версии, видно в **[бот]** `/status` (приложение передаёт свою версию в запросах).
6. **Клиенты.** `clients.protocol: <новый профиль>` → **[бот]** `/apply`. Ревизии конфигов меняются, обновлённые приложения переключаются сами. Устройства со старым приложением перестанут подключаться — им нужно обновить приложение.
7. Откат: вернуть `clients.protocol` к старому значению → `/apply`.

## 5. Справка по командам бота (админ)

| Команда | Действие |
|---|---|
| `/status` | состояние площадок и узлов, последние ошибки, версии приложений у пользователей |
| `/apply` | перечитать `config.yaml` и применить сейчас |
| `/apply upgrade` | то же + обновить пакеты на серверах |
| `/trust <узел>` | принять новый host key после переустановки |
| `/rotate tunnel` / `/rotate clients` | новые параметры обфускации |
| `/revoke_user <@username\|id>` | отозвать пользователя насовсем |
| `/unrevoke_user <@username\|id>` | вернуть доступ отозванному |
| `/backup` | прислать бэкап сейчас |
